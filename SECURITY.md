# Security policy

## Reporting a vulnerability

Email **security@classeve.com**. Please do not open a public issue for a
security problem.

Include what you did, what happened, and what you expected. A proof of concept
helps but is not required to file. We will acknowledge within three working
days and tell you our assessment and intended fix timeline. If we disagree that
something is a vulnerability we will say so plainly and explain why, rather
than letting the report go quiet.

We will credit you when the fix ships unless you would rather we did not.

Our disclosure record is at https://classeve.com/.well-known/security.txt

## What earslate is, security-wise

earslate has no backend. There is no ClassEve server to compromise, no account
database, no session store, and no audio anywhere but on the device and in
flight to the provider the user chose. This narrows the interesting surface to
three things.

### 1. The key vault

The user's provider API keys are sealed with an AES-256-GCM key generated in
the AndroidKeyStore, in StrongBox where the hardware offers it. The key never
leaves the keystore; the app stores only `base64(iv || ciphertext)` in an
ordinary preferences file, which is inert without that device.

- A fresh IV per write; the platform enforces this.
- GCM authenticates as well as encrypts, so a tampered store fails to decrypt
  rather than yielding attacker-chosen bytes.
- It **fails closed**. If the keystore is unreachable the app raises rather than
  falling back to plaintext.
- The vault is excluded from cloud backup and device-to-device transfer.
- Keys are never logged and never rendered in full to the screen.

`KeyPermanentlyInvalidatedException` is expected, not a bug: Android destroys
the key when device credentials are removed, which makes stored secrets
unreadable. The app reports this and asks for the key again.

### 2. The credential exchange

The long-lived key is used exactly once, over HTTPS, to mint a short-lived
single-use session credential. Only that credential goes on the WebSocket. A
key is therefore never resident on a long-lived connection, and a leaked socket
URL does not leak the user's key.

Provider error text is deliberately **not** surfaced verbatim — it is written
for API developers and occasionally echoes the request back.

### 3. Audio handling

Microphone capture runs only while a session is active, behind a foreground
service with a microphone type so the platform indicator is always shown. Audio
is streamed and never written to disk. Nothing is retained after a session
ends.

## Out of scope

- Compromise of the user's own provider account or key, obtained elsewhere.
- The provider's handling of audio once it arrives; that is governed by the
  provider's terms, with the user as the contracting party.
- Attacks requiring a physical, unlocked, already-compromised device — the
  keystore raises the cost of key extraction but a rooted device with an
  attacker present is outside the model.
- Reports generated by scanners with no demonstrated impact.

## Supported versions

Fixes land on the latest release. There is no long-term support branch.
